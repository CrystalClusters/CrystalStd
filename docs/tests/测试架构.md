# 测试架构设计

本文说明 CrystalStd 测试体系的总体设计：用例放在哪里、测试代码如何组织、
`test_harness` 的职责，以及 VFS 真值从哪里来。

## 1. 测试范围

测试覆盖公开接口的契约、边界行为和资源生命周期。终端颜色由人工确认项核对。
用例只存在于两处：

- `docs/tests/<模块>.md` 中的逐用例条目；
- `tests/` 下测试代码中的 `CC_CASE("<编号>", "<名称>")` / `CC_MANUAL(...)`。

## 2. 总体结构

```text
tests/
  test.c              测试入口：套件表、菜单、参数、退出码
  test_harness.h      用例与断言接口
  test_harness.c      当前用例状态、统计、失败输出
  test_header.h       各套件入口声明
  basic.c             基础组件套件
  color_print.c       彩色输出套件
  rbt_core.c          红黑树套件
  dyn_core.c          动态数组套件
  ccalloc.c           分配器套件
  ccthread.c          异步组件套件
  ccfiles.c           文件管理套件（含 VFS 行为）
  manual.c            人工确认项（全部自动套件之后运行）
```

套件表在 `tests/test.c` 的代码中维护，套件名称和标题只写在这一处。
查看当前可用套件和选项：

```bash
./run_test.sh --help
```

Windows：

```bat
run_test.bat --help
```

`--help` 的输出直接来自代码中的套件表。

文件管理套件共享同一个探针和临时目录，按场景顺序在 `test_ccfiles` 中组织；
其余套件按场景拆成独立的 `test_*` 函数。每个场景用 `CC_CASE` 标记一个用例编号，
人工项用 `CC_MANUAL` 标记。

## 3. 逐用例文档

逐用例文档在 `docs/tests/` 下，按模块分文件：

- `atoi.md`、`crc.md`、`wildcard.md`、`cctime.md`
- `color_print.md`
- `ccalloc.md`
- `cc_dyn_core.md`
- `cc_rbt_core.md`
- `ccthread.md`
- `ccfiles.md`

每个文件中的 `## <用例编号> <名称>` 就是一个逐用例条目，条目内写前置、步骤、
预期、真值来源、平台、级别和对应代码。例如 `docs/tests/ccfiles.md` 中的
`## FS-API-003 ...` 对应 `tests/ccfiles.c` 中的
`CC_CASE("FS-API-003", ...)`。

用例编号由人工分配，格式为 `模块-分组-序号`，全局唯一；删除用例后编号留空洞。
测试代码使用 `CC_CASE` 字符串引用编号。覆盖与缺陷回归用例的逐项审计见
[覆盖与回归审计](覆盖与回归.md)。

## 4. test_harness 的职责

`test_harness` 执行三件事：

1. 记录当前用例的编号和名称；
2. 统计 PASS / FAIL / SKIP / MANUAL 和断言数，并提供统一的失败信息格式；
3. 让 `all` 能跨套件汇总结果并返回正确退出码。

七个套件的公共记账集中在这里：每个套件只写测试逻辑和 `CC_CASE`，用例状态、
失败格式、计数和套件汇总由 harness 统一处理。用例定义仍在
`docs/tests/*.md` 和测试代码的 `CC_CASE` 中，harness 负责执行期记账和输出。

## 5. 运行模型

```bash
./run_test.sh                 # 交互菜单
./run_test.sh all             # 全部自动套件，随后执行人工确认项
./run_test.sh manual          # 只执行人工确认项
./run_test.sh <套件名>         # 单个自动套件
./run_test.sh all --level full --seed 123
```

Windows 对应 `run_test.bat`。

- 无参数进入交互菜单。
- `all` 先跑全部自动套件；stdin 和 stdout 都是交互终端时，在最后执行人工确认项，
  每项之间等待回车，避免长输出被控制台缓冲截断。输出被重定向时给出提示并跳过。
- `manual` 只执行人工确认项；非交互终端会报错退出。
- `--level quick|full`：`quick` 跳过耗时的压力用例，`full` 包含压力测试。
- `--seed <uint32>`：传给需要随机序列的用例；未指定时使用缺省种子。
- 测试结论直接输出到控制台。
- 任一自动用例失败时进程返回非 0；人工项单独统计。

## 6. 真值来源

用例文档中的“真值来源”使用以下类型：

- **规范**：`docs/*.md` 中写明的返回值、错误码、边界行为；
- **宿主 C 接口**：测试进程内用 `fopen` / `fread` / `stat` / `_stat` 等读取真实
  文件系统，独立于被测模块；
- **内部格式**：按 `src/ccfiles_internal.h` 定义的资源包格式，用宿主文件接口
  独立解析包字节；
- **不变量**：红黑树、动态数组、分配器自身的结构不变量；
- **人工**：终端颜色等肉眼核对项。

VFS 物理副作用优先用测试进程内的宿主 C 接口核对。目录链接/junction 等宿主 C
接口无法完成的操作调用系统 shell。VFS 真值使用现有宿主 C 接口和内部格式，
测试代码直接读取真实文件系统和包字节。

## 7. 新增用例流程

1. 先在对应模块文档中写 `## <编号> <名称>` 条目，写清前置、步骤、预期、
   真值来源、平台、级别；代码位置可以暂时写“待实现”。
2. 再在 `tests/` 中实现 `CC_CASE("<编号>", "<名称>")` 和 `CC_CHECK_*`。
3. 更新文档中的代码位置和状态。
4. 运行对应套件和 `all`，确认结论。

新增用例按“先文档、后实现”执行。
