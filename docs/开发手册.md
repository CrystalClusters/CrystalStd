# CrystalStd-开发手册

## 基础类型

`crystal_cluster.h`提供基础类型定义如下：

```C
#include <stdint.h>

typedef uint8_t CCUINT8;
typedef uint16_t CCUINT16;
typedef uint32_t CCUINT32;
typedef uint64_t CCUINT64;
typedef uintptr_t CCUINTPTR;

typedef int8_t CCINT8;
typedef int16_t CCINT16;
typedef int32_t CCINT32;
typedef int64_t CCINT64;
typedef intptr_t CCINTPTR;
```

平台检测宏定义如下：

```C
#ifdef __ANDROID__
#  define CC_ANDROID 
#elif defined _WIN32
#  define CC_WINDOWS
#elif defined __linux__
#  define CC_LINUX
#else
#  error unsupported platform
#endif
```

一些其他的基础定义详见头文件。

## 构建

各平台的构建脚本做到了 all in one，一键执行 build 即可，只区分两个平台体系：Unix Like、Windows。

运行对应平台的构建脚本：

|平台|脚本|
|---|---|
|Linux 及其他 Unix Like|`build.sh`|
|Windows|`build.bat`|

默认执行 DEBUG 构建；只有显式传入 `release` 时才启用 RELEASE 构建：

```bash
./build.sh          # DEBUG
./build.sh release  # RELEASE
```

```bat
build.bat
build.bat release
```

RELEASE 使用 `-O2 -DNDEBUG -DCC_RELEASE -Wall -Wextra -Werror`，DEBUG 使用 `-O0 -g3 -Wall -Wextra`；Windows 两种模式均额外追加 `-fexec-charset=GBK`。编译选项由顶层脚本统一传给 `scripts/build_*.sh` / `.bat` 子脚本。

- 静态库由 `src/*.c` 编译归档生成，中间目标文件输出到 `out/obj/`。
- 测试用例位于 `tests/`，编译时链接静态库 `libCrystalStd.a`。
- 演示程序位于 `demo/`，编译为独立的 `ccfiles_demo` 可执行文件，与 `test` 并列输出。

为了方便区分各平台架构，输出文件夹会根据当前平台命名，例如 Linux AMD64 架构的构建产物会放在：
```
<项目根目录>/out/linux_amd64_bin/
```
文件夹命名规则为：
```
<操作系统类型>_<CPU指令集架构>_bin
```

## 自动初始化 / 逆初始化

`src/crystal_std.c` 通过 `CC_RUN_BEFORE_MAIN` / `CC_RUN_AFTER_MAIN` 注册进程级初始化与逆初始化。具体宏定义见头文件`crystal_cluster.h`。

**静态库链接陷阱**：未使用的符号在链接阶段会被默认丢弃。但显然 CrystalStd 内部的自动初始化、卸载是静默隐藏的，不会被用户代码引用，在非全量链接时会被默认丢弃，导致无法自动初始化，功能异常。

链接 `libCrystalStd.a` 时必须满足以下任一条：

1. **全量链接该库**：

   ```
   gcc ... -Wl,--whole-archive libCrystalStd.a -Wl,--no-whole-archive
   ```

2. **只抽取相关接口**：

   ```
   gcc ... -Wl,-u,_init_crystal_std_ -Wl,-u,_deinit_crystal_std_ libCrystalStd.a
   ```

## 测试

测试用例按模块记录在 [tests 文档](tests/README.md)：一个模块一份文档，每个
`## <编号> <名称>` 条目就是一条用例，测试代码用 `CC_CASE("<编号>", ...)` 与
文档条目一一对应。测试架构、`test_harness` 的职责和真值来源见
[测试架构设计](tests/测试架构.md)，覆盖与缺陷回归审计见
[覆盖与回归审计](tests/覆盖与回归.md)。用例只存在于文档条目和测试代码。

运行项目根目录 run_test.* 脚本进入交互菜单：

```bash
./run_test.sh        # Linux
.\run_test.bat       # Windows
```

菜单中 `a` 运行全部自动测试，`m` 运行人工确认项，`q` 退出。人工确认项只在交互
终端中运行，放在全部自动套件之后，每项之间等待回车，避免长输出被控制台缓冲截断。

非交互使用：

```bash
./run_test.sh all             # 全部自动套件，终端中再执行人工确认项
./run_test.sh manual          # 只执行人工确认项
./run_test.sh <套件名>         # 单个自动套件
./run_test.sh all --level full --seed 123
```

套件名称在 `tests/test.c` 的套件表中维护。查看当前套件和选项：

```bash
./run_test.sh --help
```

`--level quick` 为默认值，跳过耗时的压力用例；`--level full` 包含压力测试。
测试结论直接输出到控制台。任一自动用例失败时测试进程以非 0 退出码结束；
人工判定项单独统计。VFS 物理副作用优先在测试进程内用宿主
`fopen` / `stat` 等接口核对，资源包按内部格式独立解析；只有目录链接等宿主 C
接口无法完成的操作才调用 shell。

## 演示

`ccfiles` 的类 shell 交互演示与测试程序并列构建为 `ccfiles_demo`，启动界面仅保留一行提示，输入 `-h` 再打印完整命令帮助，`quit` 退出：

```bash
./run_demo.sh        # Linux
.\run_demo.bat       # Windows
```

命令覆盖导航（`pwd`/`cd`/`ls`/`find`/`stat`）、挂载（`mount`/`unmount`/`refresh`）、读写（`open`/`read`/`write`/`flush`）、文件操作（`create`/`mkdir`/`rm`/`cp`/`mv`）与打包（`pack`/`unpack`）。

`write` 支持修饰符指定写入模式：

| 形式 | 说明 |
|---|---|
| `write <off> <text>` | 文本模式（默认，字面量） |
| `write -t <off> <text>` | 显式文本模式 |
| `write -x <off> <hex>` | 十六进制字节流，支持 `DEADBEEF`、`DE AD BE EF`、`0xDE,0xAD` 等写法 |

因此可手动写入任意二进制文件，写入直通物理文件（`flush` 可强制立刻落盘），其它程序即可读取。`read -x <off> <size>` 以带地址的十六进制转储回读。

> 挂载/打包等命令中的真实路径使用 `/` 分隔；相对路径基于可执行文件同级的 `res` 目录解析（与 `ccfiles_mount` 的模块语义一致）。`/` 开头的是**宿主绝对路径**——Windows 下不带盘符的 `/x` 指当前盘根（`D:\x`），不是虚拟根 `/`；要绝对路径请写 `D:/x`，或直接用相对路径。
